# Repository Guidelines

## Project Structure

This repository combines a Unity 2D Sokoban client, the 8000 FastAPI service, and the independent 8010 co-creation service. Unity code is under `Assets/Scripts/`; scenes are under `Assets/Scenes/`; preserve every Unity asset's `.meta` file. `Backend/` is the 8000 service, `Frontend/` is its static dashboard, and `CoCreationPrototype/` contains the 8010 backend and frontend. `Library/`, `Temp/`, `Logs/`, generated solution files, and `WebGLBuild/` are generated output.

Documentation and implementation entry points:

- [README.md](README.md): current product route, service/Agent boundaries, data ownership, and verification entry points.
- [CoCreationPrototype/REPLY_RELIABILITY.md](CoCreationPrototype/REPLY_RELIABILITY.md): component acceptance, request budgets, recovery, audit metrics, and 8010 deployment/rollback.
- [CoCreationPrototype/Backend/evaluations/README.md](CoCreationPrototype/Backend/evaluations/README.md): isolated semantic evaluation scope and commands.
- `CoCreationPrototype/Backend/app.py` and `repository.py`: API state, persistence, idempotency, deadline, and research projections. `llm_client.py` and `design_context.py`: role-specific LLM context and semantic memory. `design_requirements.py`, `revision_workflow.py`, `proposal_search.py`, and `level_validation.py`: requirements, execution constraints, search, snapshots, and solving.
- `Multi-Agent/` contains role descriptions and historical examples; do not restore obsolete flows from those examples. `SERVER.md` and the research PDFs/action plan are local, non-distributed references. Do not invent missing reference files.

Keep these documents consistent with confirmed revisions and implementation. A documentation discrepancy or existing implementation bug does not authorize changing the study design or weakening its guardrails. The 2026-10-02 requirements policy and 2026-10-03 component-recovery rules supersede older conflicting descriptions; the 2026-10-06 reporting/evaluation tools do not change runtime behavior.

## Current Product Baseline (reviewed 2026-10-07)

- The active online route is `Menu -> Questionnaire(Online1) -> Online_Lobby -> Match_Briefing -> DG -> DG_Level -> CoCreation_Entry -> 8010 -> Challenge_Waiting -> Online_Level -> Match_Result -> Questionnaire(Online2) -> Menu`. Both online questionnaires are part of every match cycle: Online1 opens the pre-match WJX survey before the lobby, and Online2 opens the post-match WJX survey after results. Do not add a persistent skip flag.
- The Unity `Draft` scene is retired; the immutable `draft` event remains an 8000 dashboard research record. PC code, scenes, and backend capability are retained for later work but have no Build Settings entry, menu/navigation route, or current client integration. Do not restore them without a confirmed study-design revision.
- DG asks four neutral map-design questions (first-move inspection, push dependencies, space distribution, and route rhythm). AI returns a warm reflection plus difficulty and layout recommendations; Q1–Q2 infer difficulty and Q3–Q4 infer layout. Confirmed DG context guides only the 8000 first-draft generator; it must never be sent to, persisted by, or exposed in the 8010 service or its LLM context.
- Menu's `Tutorial` button opens the static bilingual PDF at `https://sokobanaidemo.top/frontend/tutorial/Sokoban_Tutorial_Bilingual.pdf`. It opens in the browser's PDF viewer and does not enter a Unity route.
- The documented Agent roles are `Draft首版理解助手` and `关卡蓝图规划助手` on 8000, plus `共创聊天助手` and `共创关卡修改助手` inside 8010. The deterministic generator, executor, validator, and Sokoban solver are not Agents.
- Stage openings, translations, turn understanding, requirements review, and intent reviews are auxiliary LLM tasks, not additional product Agents. The current system uses controlled workflows, role-specific context, and deterministic execution checks; do not equate a new report or evaluation suite with improved model understanding or a new autonomous-agent architecture.
- Model isolation is mandatory: the two 8000 Agents keep `deepseek-v4-flash`; the two 8010 Agents and all 8010 auxiliary LLM tasks use Kimi `kimi-k2.6` through the Moonshot endpoint. The 8010 service must not read or silently fall back to 8000 `DEEPSEEK_*` variables.
- 8010 Stage assessment remains a backend archival record only; the frontend must not render a Stage assessment card. Stage 1's fixed operation guidance is appended by the backend exactly once. Historical Stage 1 openings receive the same read-time compatibility repair without rewriting the database.
- Kimi responses use the final backend output chain: parse, remove internal fields, validate current-Stage coordinates/routes, apply DesignContext rules, then append the Stage 1 closing only for the Stage 1 opening. `designContextPatch` and `coordinateLinks` remain backend metadata and are never visible cards.
- 8010 map facts have one authority: construct a `StageSnapshot` from the immutable current version rows, version ID and entity bindings. Chat, openings, proposal/revision, route restoration, translation, modifier-agent prompts and execution checks may use only that snapshot. Never pass old Stage rows, historic assistant coordinates, user-supplied mistaken coordinates, duplicate map facts, or old route conclusions as current map evidence.
- LLM prose is treated as analysis, route reasoning or personal reflection; current coordinates, tile states, entity positions, route endpoints and underline text must be rendered or revalidated by the server against the snapshot. Invalid current-map sentences are dropped without turning them into DesignContext, cards, proposals, routes or map edits. Ordinary chat and route discussion may display only validated Kimi prose: they retry Kimi up to three times within the existing 120-second budget and return a retryable request error without an assistant turn if no reliable prose remains. Server-snapshot fallback prose is reserved for explicitly defined flows such as Stage openings and must never replace an ordinary chat reply.
- Relevant map discussion should normally retain 1–2 concise route-reasoning passages and one concrete first-person reflection, without becoming a solver trace. If output exceeds presentation budget, compact only repetitive route reasoning and reflections; do not reject or discard an otherwise valid response. Translation prompts must not receive snapshot internals, but their returned body and coordinate-link text must be revalidated against the source turn's snapshot.

## Unity Authoring

- When changing a Unity scene, use a connected Unity Editor through MCP. Do not hand-edit scenes, prefabs, or serialized Unity YAML while MCP is available.
- UI must be static, scene-owned, and Inspector-serialized. Do not inject temporary prefabs, create visible controls at runtime, or bind production UI through object-name/path lookup.
- DG keeps world-space grid/camera objects outside `DGCanvas`; all visible DG controls are static children of `DGCanvas`. DG flow changes text and button interactivity, not UI GameObject activation.
- `Online_Level` starts its 30-second opponent challenge timer only after the player gains control. On timeout it locks input, submits a `timed_out` result, and shows the static `ChallengeFailPanel`; `Match_Result` must show timeout and the recorded move count distinctly from completion.

## Research and Co-Creation Guardrails

- `Assets/EssayBase/8-3/SURF_Feedback.pdf`, `Assets/EssayBase/8-3/Feedback_Action_Plan.md`, and the confirmed route in `README.md` are the planning baseline. If a request conflicts with them, identify the conflict and wait for explicit confirmation before implementing; update the relevant planning document with an approved revision.
- Keep researcher-defined goals or conditions out of LLM-visible prompts. The neutral co-creation flow records a designer's self-reported intention only after final Stage confirmation and before opponent results.
- Formal draft regeneration reuses the last valid, deep-copied Unity blueprint with a new seed and frame-sliced deterministic generation/validation. It must not call the 8000 LLM again or silently replace that blueprint with algorithm-only generation. 8010 stores only the latest candidate rows, not DG context or the blueprint. Formal work requires the same `/game/` iframe and version-5 bridge preflight; delivery ACK is not task completion. Pending/claimed regeneration leases are 60/120 seconds; failures preserve the previous draft. Normal workbench controls do not expose a refresh action; handshake recovery preserves same-Stage unsaved edits locally.
- A co-creation session contains one level. `Stage 1`, `Stage 2`, and later names are immutable versions of that level, never separate levels or progression.
- Preserve turns, versions, proposals, decisions, play evidence, timing, final rows, intention, and opponent outcomes. A level is sent to the opponent only after explicit final confirmation.
- The LLM is a warm, first-person design peer. Its interpretations of intention must be tentative and correctable; it must not attribute generator-placed DG tiles to the designer, claim unsaved edits were made, or create/accept a map proposal without explicit authorization and deterministic validation.
- The 8010 workbench for formal Unity sessions begins a persistent 20-minute deadline only when the user selects `Enter co-creation flow` and the latest draft preview is atomically promoted to Stage 1. Preview access, refreshes, and regenerations do not start the timer. After expiry, chat/edit/save/restore/play/proposal/language actions are locked; only final Stage submission remains. A valid unsaved local draft may be atomically saved as the final `human_edit` Stage when submitted. Direct `/cocreation/` demo sessions have no deadline and remain available for the current test.
- The 8010 flow is a two-role handoff: `共创聊天助手` understands the request, asks for clarification, and produces an authorized semantic `RevisionPlan` plus `executionContract`; `共创关卡修改助手` receives only that contract, the current Stage, deterministic map facts, and solver metrics, then returns local operations. It must not receive full chat history, 8000 `dgContext`, researcher goals, experimental conditions, or unconfirmed intent hypotheses.
- The 2026-10-07 proposal-semantics revision separates evidence-bound goals, requested edit components, spatial focus and preservation. Critical permission/scope changes and legacy-topic reconstruction require independent Kimi review within the same request deadline. References to protected entities never imply moving them; aesthetic goals do not require gameplay-route changes or a fixed solver witness. Historical records stay immutable.
- New ordinary messages use Kimi `turn_understanding` with exact latest-user evidence, current StageSnapshot, recent user wording, and bounded proposal-topic context. Keep evaluation, intention, explanation, conceptual ideas, concrete revision requests, and protected-entity changes distinct; do not infer an edit request from a visual comment or gameplay discussion. An unclear direct change request uses bounded clarification; ordinary questions/ideas remain prose. Optional TENTATIVE INTENT must be substantive and correctable, not mandatory filler. A new `LET'S DISCUSS` card requires a structured disagreement; retain read-time compatibility for legacy turns. Cards never authorize or apply a map change by themselves.
- The composer `Proposal` button toggles the next message's mode; it does not immediately send. Enter/Send transmit unchanged input with the selected `requestProposal` flag. Reset the toggle on success; restore the original flag, text, Stage, and idempotency key on retry. An active persisted proposal topic continues through short answers even after the toggle resets. Do not permit a new proposal/card action during an active disagreement.
- One current-Stage `proposalDiscovery` topic may display at most three high-value clarification questions, counted from final visible output rather than response turns. Multiple questions, protected-object branches, repairs, and retries share that budget; an idempotent retry must not count twice. Bind short answers to the topic, reconstruct its complete persisted history, and stop asking once the budget is exhausted. If sufficient, plan early; otherwise conservatively bind unspecified editable objects within permission bounds. Do not demand exact coordinates, invented push targets, or a fourth question. Preserve `retry_pending`/`revision_needed` topics and their request, answers, supplementary direction, and failure evidence; only success, explicit cancellation, or Stage change ends the topic. Model-validation failure must not replace a proposal request with generic Stage-opening prose.
- All 8010 Kimi tasks use `thinking.disabled`, including `RevisionPlan` and modifier-operation candidate requests. Structured proposal phases emit direct JSON at `temperature=0.6`; hidden thinking must never consume their completion budget or reach turns, DesignContext, cards, routes, or audit-visible content.
- Both AI proposals and saved human edits pass a risk review. `WARNING` is conditional and requires concrete map, solver, play, or explicit-goal evidence; a different proposal, rejecting AI, or using the editor is not evidence by itself. A validated human edit remains in place and receives two consecutive assistant turns: a card-free Stage observation followed by an always-visible comparison against verified diff, solver/play evidence, confirmed DesignContext, and bounded Stage lineage. Only an evidence-backed conflict adds `LET'S DISCUSS`; that human-edit disagreement card appears only on its entry turn. Later discussion uses ordinary bubbles, and Kimi may return human-edit-only `acknowledged` when the designer explicitly agrees to discuss, explain, adjust, modify, or re-edit; this clears the proposal block without choosing a winning position or recording a confirmed decision. During an active human-edit disagreement, the same Kimi reply must bind that status to an exact evidence span from the latest designer message; missing, invalid or inconsistent engagement metadata consumes the existing retry budget and ultimately returns the retryable chat error without restoring the old active disagreement or saving an assistant turn. The human-edit review does not add `WARNING` and never auto-reverts or overwrites the edit.
- Standard purple `REVISION` cards expose `execute_revision`, `challenge_revision`, and `alternative_revision`, subject to server `availableActions`. The current challenge first reply only invites the reason; primary/secondary hypotheses remain structured tentative records. A clear reason produces one `ai_revision_challenge` choice card with `challengeCardSchemaVersion=2`; continued/ambiguous answers use ordinary bubbles without repeating the card. `choice_pending` yes (`ai`) revalidates the original frozen tiles and creates a pending proposal; no (`user`) carries the original request and canonical reason, excludes the old candidate from generation/repair/search, and produces a newly validated purple card with only `execute_revision`. Choice buttons and unambiguous text use the same transition. Neither path creates a Stage until the pending proposal is explicitly accepted. Preserve historical records without re-emitting obsolete card sequences. Alternatives must differ from the cited proposal; active disagreements cannot produce purple proposals. `retain_current` ends a disagreement without a Stage.
- A converged proposal follows `RevisionPlan → semantic executionContract → operation candidates/search → exact executionBrief freeze → structure checks and validate_and_solve()` before its purple card is shown. Replay those exact transitions after `execute_revision`, recheck permissions/constraints and solve again, then require acceptance of the pending proposal to create a Stage. The original Stage remains unchanged on every failure. Explain verified, partial, and unverified goals; one solver route does not prove all solutions require a given switch pattern or that real play takes longer.
- Current `requirementRecord` distinguishes fixed `invariant` requirements, explicit non-reversing `goal` directions that may be partially fulfilled or traded off, and ambiguous `preference` items. Retain each requirement's original user evidence and Turn; compile with Kimi and independently review, then validate properties, units, values, entities, and exact transitions. Do not derive quantities from concatenated chat, keyword proximity, or B1/T1 labels. Reject fixed-rule conflicts, protected edits, exact-transition failures, and goal reversal; no generic WARNING for search failure or rejecting AI. Choose candidates by explicit priority, current focus, other goals fulfilled, fewer changes, then stable strategy order. Automatic bindings are proposal assumptions, not confirmed user intent or a withdrawal of other goals.
- Revision Workflow V2 retains stable IDs and shared requirements across model candidates, one corrective replan, bounded deterministic search, and execution replay. Demo defaults to `enforce`, formal sessions to `shadow`, but current `requirementPolicyVersion=1` fixed/direction/permission checks reject invalid candidates in both modes. V1 cards retain their frozen-diff compatibility, not permission to reinterpret old consent. Challenge hypotheses, state, and reason reviews are canonical records; a two-attempt review failure keeps one user Turn plus internal `review_pending`, returning the retryable error so ordinary retry reuses the key. A substantive replacement supersedes the old review. No dedicated review/supplement/exit controls; resolve challenges through conversation and the existing choice card. Resolve challenge routing before semantic side effects.
- Every actionable `proposalOffer` carries a hidden exact `executionBrief`: `effect`, `anchors`, `focus`, `requiredTransitions`, `allowedOperators`, `preserve`, and `playObjective`. Semantic planning may leave transitions empty unless the designer explicitly named them; after a candidate passes, the server freezes its real diff into non-empty transitions. Explicit coordinates and `from → to` transitions remain hard constraints. Candidate repair deduplicates across attempts, and bounded deterministic search uses the same semantic contract, mechanism evidence and solver checks.
- Within the current Stage, only the latest assistant turn with a valid `proposalOffer` may receive `execute_revision`, `challenge_revision`, or `alternative_revision`. Older purple cards remain visible but read-only in the frontend, and the backend must reject stale `sourceTurnId` values with `INVALID_CARD_SOURCE`. Ordinary assistant turns without `proposalOffer` do not make the latest proposal stale; accepted map-proposal controls are separate.
- Every `level_versions` row also owns a server-maintained `design_context_json` snapshot. Child Stages clone the parent's DesignContext before adding their own confirmed/rejected decision or later user evidence; parent snapshots remain immutable. `explicit` means the user said it, `confirmed` means a user/formal action established it, and `inferred` is an AI hypothesis only. Inferred memory must never become an execution hard constraint or overwrite explicit/confirmed memory.
- Chat, Revision, and human-edit/Evaluator review use role-specific projections of the same DesignContext. Revision receives active explicit/confirmed goals and constraints, confirmed/rejected decisions, relevant open questions, and the execution brief, but never full chat history, 8000 DG context, researcher conditions, rejected/pending/tentative inclinations, or inferred intent as a hard requirement. The snapshot must not be confused with final `designer_intentions`.
- Normal chat may return an optional `designContextPatch`; validate evidence, derive explicit memory from user language, downgrade model claims to inferred, and drop invalid optional patches without blocking reliable prose. Ordinary non-proposal turns use a main `intentDecision` plus Kimi `intent_candidate_review` for false positives/negatives, exact evidence, semantic claims, and consistency with confirmed inclinations. Reviewed claims are locked; do not rewrite them through keyword heuristics. Repair body/card components separately, preserving valid components. Sentence/length/style signals are soft; original evidence, direction, conflict IDs, StageSnapshot grounding, truncation, and semantic scope remain hard. Vague visual feedback must retain uncertainty about appearance versus play effects. Legacy keyword-derived claims remain `legacy_unverified`, not deterministic conflict evidence.
- Orange TENTATIVE INTENT is optional, ordinary-turn-only, substantive, evidence-aware, and explicitly correctable. Only the dedicated feedback endpoint confirms/revises/rejects it; free-text yes/no does not change its state. Rejection makes no LLM call. Confirmation with existing inclinations and every revision use `intent_feedback_review`; unclear/conflict outcomes remain audit-only pending with the same hypothesis ID and compatible adjustment controls. Reviewed explicit opposite claims on the same object/property may use deterministic existing/new inclination selection; broader scope/experience/priority conflicts follow the review. Pending/rejected/tentative inclinations never enter Revision. Conservative startup migration must never infer intent from assistant prose alone.
- The frontend co-creation progress panel renders two Stage-snapshot sections: `Unresolved questions` and confirmed/revised `Design inclinations`. It extracts questions only from final visible non-orange-card assistant output, uses a bounded Kimi review to mark genuinely answered questions, and keeps answered or ignored items in a collapsed `Processed` history. Current open questions can be deterministically ignored without an LLM call or conversation turn; ignored questions leave all LLM contexts and can return to open only through the user-facing `Restore` / `恢复` action. Every inclination includes a Stage-attributed “Why I understand it this way” trail capped at 12 entries and limited to explicit expressed directions, confirmed proposal/disagreement decisions, and verified manual-edit observations. Orange-card questions never enter question progress; confirmed orange-card content is rewritten into the inclination statement. Historical Stages must never include descendant answers, ignore/restore state, memory, or evidence. Compatibility fields remain in the API even when the current UI no longer renders them directly.
- Base `/cocreation/` visits show a loading landing/draft preview and automatically create an `algorithm_demo` 10×12 map using the Algorithm_Level-inspired two-box/two-target, water, structure-template, and reverse-pull flow. Regeneration replaces only the candidate; explicit entry promotes Stage 1. Keep only the latest successfully created demo session; a failed replacement preserves the old demo. Do not clear formal sessions, sync to 8000, start a formal deadline, or write matching records.

## Reply Reliability, Reporting, and Evaluation

- Reliable body and full presentation quality are separate. Optional intent cards, memory patches, links, and question reviews must not discard an independently valid body. Required evidence, disagreement/intent-conflict state, authorization, map facts, contracts, and solving continue to block their corresponding conclusions/actions. Ordinary chat without reliable Kimi prose returns the retryable error without an assistant turn; no Stage-opening fallback.
- Current requests share the HTTP entry's 116-second internal deadline inside the 120-second backend budget. Ordinary prose has at most three attempts; requirements compilation/review and challenge reason review each retain two attempts. Optional work shares at most 10 seconds total and reserves 20 seconds. Do not reset the deadline inside subtasks/recovery, or use legacy 300-second proposal constants for current requests.
- Lock valid requirements while locally repairing failed items, then re-review complete coverage. Cache only fully verified requirements; key by exact StageSnapshot, user sources/content, answers, decisions, DesignContext projection, language, and policy/prompt versions. A correctly understood but infeasible proposal may deliver validated Kimi failure analysis without a purple card or map change; unreliable understanding, permission failure, and upstream failure do not authorize that recovery.
- Keep successful human saves when review fails; atomically recover the two complete review messages without another Stage. Translation commits per turn, keeps successful results and source-language text for failed items, and retries only unfinished items. Frontend timeout includes send/read/parse; invalid 2xx bodies are failures. Reuse captured input, action, Stage, draft, mode, and idempotency key on write retries; refresh read-only to confirm server commits.
- `reliability_report.py` reads audit events in SQLite read-only mode, never reads chat prose or calls Kimi, and reports task-based logical requests, issue symptoms, body recovery, verified proposals, and recorded generation latency. Group by session/task/message key; challenge review joins its message, stage openings stay separate. Missing generation/body/quality booleans are unknown, `rate` uses `observed`, and multiple outcome records are not exact HTTP retries or model attempts. Error codes do not prove misunderstanding or false rejection; browser delivery, pre-audit failures, human quality, and token costs remain unobserved. Do not infer success from small samples or an empty issue list.
- `semantic_eval.py validate/score/compare` are offline. The current suite has 36 synthetic turn-understanding cases and two solvable maps, not full chat/proposal/challenge coverage. Only explicit `run --live` enables billed Kimi sampling; it uses the production understanding entry without online HTTP, session creation, SQLite writes, or DeepSeek fallback. Expected answers, case labels, review notes, researcher goals, and conditions must not enter model input. Missing runs stay in the denominator; comparisons require identical suite hashes and repeat counts. Mark/de-identify any future real cases; preserve original research records. Keep outputs under ignored `CoCreationPrototype/Backend/evaluation_runs/` and never present fixed-output tests as real-model accuracy.

## Online Match and Deployment Rules

- Match room results use `completed` or `timed_out`; legacy results without an outcome are treated as completed. Do not regress idempotency, room identity, or result polling.
- The canonical public endpoints are `https://sokobanaidemo.top/game/`, `/frontend/`, and `/cocreation/`; HTTP, `www`, and direct IP requests redirect to the HTTPS apex domain, and public links never use `:8000` or `:8010`.
- WebGL Dashboard access is gated in the game page itself: the footer `DATA DASHBOARD` button must validate the existing password before opening `/frontend/`; do not move the first prompt back into the 8000 page.
- The Online Lobby uses static browser-native WebGL template inputs for room codes: the generated code is read-only and selectable for manual copying, while the join field accepts paste and normalizes a six-character alphanumeric code. These fields synchronize with Unity through `BrowserNavigation.jslib`; there is no `COPY CODE` button.
- The 8000 dashboard keeps full Match IDs and Study Session IDs in the data model, displays their first eight characters with copy-full-value controls, and searches both players' complete or short Study Session IDs. Record details show both players' Study Session IDs on every flow node.
- The 8010 `final` event records server-derived `coCreationDurationSeconds` in the 0–1200 second range; opponent play time remains the 8000 `result_submitted.durationSeconds` field.
- When a requested change is safely deployable to the server, deploy it autonomously after verification. Do not build WebGL autonomously; if a WebGL build is required, ask the user to build or provide it, then upload that build when requested.
- For an 8010-only deployment, use SQLite's online backup API for a consistent database backup, preserve replaced files and hashes, and upload only changed `CoCreationPrototype` files. Restart only `sokoban-cocreation` when service code changes; docs, static assets, and isolated offline tools do not by themselves require a Python-service restart. Never use `/root/SURF/deploy_scp`, restart 8000, or build/upload WebGL for an 8010-only change. Check both origin and public health/ready plus affected assets; do not create a new production demo for verification, since it deletes the previous demo. Code rollback must not overwrite intervening research data with an old database. Keep backup/diagnostic files out of Git.
- From Windows, production SSH and SCP must explicitly use the non-default private key `%USERPROFILE%\.ssh\sokoban` with `IdentitiesOnly=yes` (for example, `ssh -i "$env:USERPROFILE\.ssh\sokoban" -o IdentitiesOnly=yes root@111.231.136.4`). Do not rely on OpenSSH's default `id_*` key discovery, and never upload or print the private key.
- For a WebGL update, use Unity `2022.3.62f2c1` only when the user has built or explicitly requested the build, bump the WebGL template cache key when browser assets can be stale, upload `WebGLBuild/`, and verify the public index plus loader/data/framework/wasm responses. Uploading `Frontend/tutorial/` alone does not require an 8000 restart.
- Do not commit `.env`, API keys, SQLite databases, research logs, Unity caches, or generated WebGL output. Preserve unrelated user changes in a dirty worktree.

## Build, Test, and Style

- `python Backend/app.py` starts 8000; run `python -m unittest discover -s Backend -p "test_*.py"` for its tests.
- `python CoCreationPrototype/Backend/app.py` starts 8010; run `python -m unittest discover -s CoCreationPrototype/Backend/tests -p "test_*.py"` for its tests.
- Frontend checks: `node --test CoCreationPrototype/Frontend/tests/*.cjs` and `node --check CoCreationPrototype/Frontend/app.js`. Offline suite validation: `python CoCreationPrototype/Backend/semantic_eval.py validate`. Do not make a normal regression or documentation check call the real model.
- Generate Unity project files through the Editor before using `dotnet build Assembly-CSharp.csproj -v:minimal` as an optional C# compile check; it does not replace Unity Test Runner or validate a WebGL build. `Algorithm_Level` is an enabled standalone experience, not part of the formal online route.
- Use Unity `2022.3.62f2c1`; run Unity tests through Test Runner as appropriate. Do not build WebGL unless requested.
- Use four-space indentation. C# types/methods are `PascalCase`, C# fields/locals are `camelCase`, and Python uses `snake_case`. Add focused regression coverage for behavior changes; tests must not require a real API key or network call.
