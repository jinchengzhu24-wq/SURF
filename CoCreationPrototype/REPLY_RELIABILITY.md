# 8010 回复可靠性与流程恢复

本文件维护 8010 对话、设计记忆、提案、执行、恢复和诊断的现行契约。修改这些路径、前端卡片或模型协议前应阅读相关章节。正式路线、入场、Stage 生命周期及研究数据边界见 [研究流程](../docs/STUDY_PROTOCOL.md)。协作历史在 Git 和本地 `AI_Exchange/` 查阅。

## 回复与地图事实

- 当前地图的唯一权威是 `StageSnapshot`，由当前不可变版本的 rows、版本 ID 和实体绑定构成。对话、开场、提案、路线恢复和执行验证使用这份快照。旧 Stage rows、助手的旧坐标和路线、用户说错的坐标只可作为待核实的讨论信息。
- 每条请求的 `dialogueEvidence` 保留真实 Turn ID、Stage 和用户原话。范围为当前 Stage 最近 24 条 Turn 加活动主题已固定的用户来源，各角色使用自己的投影。历史原话可解释目标，授权新动作或变更当前状态须绑定当前用户原话或正式操作。助手建议不产生用户约束。
- 模型给出分析、建议或有依据的个人判断。输出在服务端完成解析、内部字段清理、坐标和路线验证及 DesignContext 处理。地区、实体、格子、可达性、路线端点、正文下划线必须按快照重建或重新验证。路线文字须与可见正文精确对应。错误地图句和依赖它的结论不进入回复、记忆、卡片或提案。`designContextPatch` 为内部元数据，`coordinateLinks` 仅投影验证后的链接。
- 先答当前问题，给必要依据。短而相关的回复有效，长度、句数、少量语言混用和幽默只影响表达。路线分析按需要提供，避免求解器逐步转录或重复反思。助手以第一人称给出可纠正的理解，不把生成器放置的格子归功于设计者，不虚构试走或未保存的操作。
- 正常正文、可选卡片、链接、进度和记忆分别验收。可选组件无效时保留已验证正文。明确的正文缺陷仍须修。普通聊天和路线讨论最终须交付可靠 Kimi 正文，耗尽则返回可重试错误且不写助手回合。只有已定义的 Stage 开场等流程允许使用快照兜底。
- Stage assessment 只归档，前端不显示独立评价卡。Stage 1 开场由后端追加一次固定指导，涵盖试玩、局部编辑、小范围可审查协助和由设计者主导的大改。旧开场在读取时兼容显示，原记录保持。人工编辑的观察和比较各承担不同内容。

## 请求预算、幂等与提交

| 边界 | 当前要求 |
| --- | --- |
| 模型传输 | 8010 各任务使用 Kimi 的 `thinking.disabled`，结构化方案任务用 `temperature=0.6` 和直接 JSON。优先使用匹配任务的严格 JSON Schema，只在提供商不支持时按原规则降级为 `json_object`，服务端继续完整验证。两个精简实验开关独立、默认关闭。 |
| 主请求 | 服务端预算 120 秒，从 HTTP 入口建立 116 秒的内部绝对截止时间。普通正文最多三次。需求编译、独立复核、质疑理由复核各沿用原有两次上限。入口理解、关键独立复核的单次上限为 25/18 秒。可选工作累计最多 10 秒并预留 20 秒，必需语义使用主预算。旧 300 秒常量不用于当前消息流程。 |
| 浏览器 | 消息 125 秒超时包括发送、读取和解析，非法 2xx 视为失败。写失败先只读刷新，刷新确认 Stage 和原键后按保存情况恢复。重试带回原文本、动作、来源、Stage、草稿、方案模式和幂等键。 |
| 消息身份 | 同一会话的键绑定原正文、基础 Stage、动作及来源、方案模式。用户回合之前的理解失败按存量失败签名核对，之后失败复用已存用户回合和仍有效的理解。回放已保存回复须先校验身份、序列化并提交，再重试原在线同步。已答复回放与未完成请求的当前 Stage 校验保持各自顺序。 |
| 并发提交 | 末次写事务复核活跃会话、当前 Stage、地图与实体、设计上下文、最新用户回合和适用的 HTTP 接收凭据。过时方案、探索结果或卡片动作返回 `PROPOSAL_STALE`。普通正文仅在独立可靠时交付，清除过时卡片、状态声称、记忆及问题更新。保留同键锁、已有审计和本地原子性。 |

`lastMessageFailure` 只投影当前 Stage 可匹配的最近尚未交付消息故障，支持理解阶段尚无用户回合的情况。匹配原 Stage 和键后才展示可靠代码、阶段和尝试信息，成功回复清除旧失败。原始模型输出、提示词及凭据不进入公开失败详情。

请求编排与绑定见 [消息路由](Backend/cocreation/api/routes_messages_and_proposals.py)及 [上下文构造](Backend/cocreation/api/context_and_discovery.py)。

## 回合理解与证据复核

`turn_understanding` 区分评价、说明、意图、概念思路、具体修改和固定对象变更。普通评价或讨论不自动触发方案。范围、焦点、目标和保留要求各自绑定真实原话及来源 Turn。提及玩家、箱子、目标或外围区域可以是参照或玩法讨论。实际要求改变保护对象时，由复核确认原意后说明限制。普通入口校验的特定失败可只讨论，仍须有可靠 Kimi 正文，且关闭提案、记忆和状态更新。活动方案主题的理解失败保留原主题与原键，不能回落普通对话。

关键权限、范围变更、既有目标或保留条件撤回以及旧主题的必要重建，使用独立 Kimi 复核。当前 `understanding-delta-3-quote-leaf` 协议由服务器提供目标和基准。`APPROVE` 沿用校验过的对象，`CORRECT` 只接受目标对应的原生 JSON 值与可追溯原文，`REJECT` 安全停止。语义纠正允许替换指定项或追加遗漏项，禁止整对象覆盖、删除、重排、字面复制/交换或追加重复条目。

当前协议中，复核后的技术修补只可调整结构完整且绑定明确的纠正项中的精确 `evidenceSpan` 叶子。其他字段、来源、顺序、结论和已有项均锁定，合并后对锁定内容执行整体比较。非叶子、结构错误、错绑及目标歧义都安全失败。继续核对完整主题、权限和原文覆盖。引文存在仍需语义复核。有效旧记录不回写，只有匹配现行复用版本及绑定的理解才可再次使用。相应作用面见 [证据复核实现](Backend/cocreation/domain/understanding_review.py)。

## 方案发现与三问上限

点击 `Proposal` 是下一条消息的模式开关。发送按钮或 Enter 携带原输入和 `requestProposal`，成功复位，失败恢复前一节规定的完整请求。同 Stage 的已存在主题按自身策略继续。活跃分歧阻止新提案和紫卡动作。

### 现行 Policy 2

新建合格提案主题默认进入 `discoveryPolicyVersion=2`，初始请求自由输入。主动 Proposal 或经过验证的具体修改可以进入该路径，已有主题、活跃分歧、仅对话模式和确切的保护对象修改由原分流处理。

- 信息充分时提前规划。需澄清时每次最多发布一道问题和两个有实质差异的 A/B 按钮，可带简短取舍说明。同一主题最多发布三道题，幂等重试、不成功的发布或翻译不消耗题数。澄清中只能使用当前按钮或专用取消，禁止自由文本绕过、换一组或改旧答案。取消不调用模型、不创建 Stage，规划中按现有租约和忙碌保护处理。
- 两个选项各有基于同一不可变 Stage 的可执行、可解候选。先验证当前权限、真实结构、授权合同、已有固定要求以及历次选择的累计动作。全主题共用总改动预算，至多 12 格。初始要求、策略、问题和标签共用既有澄清生成与独立复核槽，后续步骤复用已复核的初始要求。确定性预检、基准、修复重验与求解共用最多 20 秒并服从绝对截止时间及余量，两分支各有界执行。禁止增加单独的可行性模型调用。
- 明确兑现选项中的技术动作，例如减指定障碍、实际拓宽通道、减少同一最短移动指标或保持约定数量的水域移位。仅可解或操作同名不足以证明兑现。目标和保留条件允许时优先考虑移除障碍。排布或外观目标本身不授权删除。真实游玩时间、体感难度、美观均须另行观察。
- 选择端点 `POST /api/sessions/{session_id}/proposal-discovery/choices` 绑定当前 Stage、主题、问题、选项、展示语言和键。取消端点 `POST /api/sessions/{session_id}/proposal-discovery/cancel` 绑定 Stage、主题和键。按钮提交绑定的 ID，服务器从已展示语言组解析，并原子记录收据及选择证据。重复点击只恢复原请求，过期按钮与冲突原键拒绝。未保存编辑时保持前端限制。
- 初始候选、证明、实施格子和参数只保存在私有主题状态。公开 `proposalFlowState` 提供问题、标签、当前状态和可重试动作。隐藏假设不变成用户固定要求。选择只证明该题的取舍，不确认橙卡、不形成全局倾向、不授权改图。可重试失败保留原键和选择，不再消费题数。取消后原失败键不能重启主题。
- 最终要求编译和独立复核覆盖每项真实选择。沿原约束验证和搜索恢复条件使用缓存，重验当前绑定、权限、合同、真实操作、求解及所有已选动作。交付紫卡时展示实际改动、选择关联、已验证和待试玩边界。无合格候选不出紫卡，末次状态变化按写事务拒绝。翻译按整组处理问题、说明和 A/B，固定 ID、字母及顺序，复核失败保留整组源语言。

入口及动作检查见 [收据与路由](Backend/cocreation/api/binary_routes.py)、[动作验收](Backend/cocreation/domain/binary_discovery.py)和 [生成与独立复核](Backend/cocreation/llm/binary_model.py)。

### Policy 1 兼容

已持久化的旧主题和旧卡保持自己的兼容路径，避免把已有自然语言答复转换为 A/B 点击或迁移历史。旧主题可用短文本回答最近的有效问题，按最终可见问题数共享三问上限，重试、备选变化和局部修补不重置次数。信息充分可提前规划。预算结束后保守绑定可编辑对象或保留原主题并报告必要的冲突，避免第四问和猜测授权。解释选项、排除或更正方向分别根据原话复核，解释请求本身不产生选择。能恢复的请求沿用原键，兼容旧主题在本地捕获的请求丢失且无法恢复时重新输入。`retry_pending`/`revision_needed` 保留原申请、已答问题、补充方向与失败依据，正常结束事由为成功、明确取消或 Stage 变更。

旧澄清语法由服务端按持久化策略和锁定/修订状态决定。基础格式是 `body`/`question`。启用旧备选结构时可提供通常两个、至多三个方向，并使用 `options`、`comparedOptions` 和 `discriminant`。锁定复用时 `options=null`，复核另需 `optionIssues`。这些字段只属于相应兼容分支。题目须区分实际选择取舍，失效选项或复核失败走既有纠正与重试，禁止固定问题绕过验收。保持提示、Schema、解析与纠正指令一致，绑定实际展示选项，存量冻结差异继续按原授权重放。[旧选项校验](Backend/cocreation/domain/proposal_options.py)

## 提案履约与紫卡

1. 从用户原话和已选动作编译 `requirementRecord`，独立复核属性、实体、单位、范围、值和显式转换。实体编号、词语距离与拼接历史不能代替明确的数量证据。`invariant` 为不可放宽约束，`goal` 可部分满足或取舍但不得反向，`preference` 保留不确定性。固定要求之间矛盾先处理。只复用完整验证且匹配 StageSnapshot、用户来源、主题答案、决定、设计投影、语言、策略和提示版本的要求缓存。
2. AI 按授权范围编辑水域和内部墙。保持外壳、玩家、初始箱子、目标点及受保护格子。墙体授权不延伸到水域，水域授权也不延伸到墙体。视野焦点或默认实现对象只表示方案假设。明确坐标和 `from → to` 为硬边界。定性视觉方向使用 `appearance/seek`，不造数值或统一要求改变玩法路线。`original_cells` 的保留计数从当前 Stage 原有格集合求交集。总数量、是否移除、范围和优先级分别根据原话判定。
3. 聊天助手产出授权 `RevisionPlan` 与 `executionContract`。修改助手只接收合同、当前快照、确定性事实及求解指标，输出局部操作。完整聊天、未确认倾向和正式研究条件不在交接中。V2 候选、确定性搜索、已有一次纠正重规划和重放共用稳定的要求 ID、约束、权限、去重、总预算及验证。允许在同一获准组件内同时删加以实现目标，明确保留位置或禁止删除时生效。候选按明确优先级、当前焦点、其他目标、更少改动、稳定策略顺序排序。
4. 候选须有相关实际改动，通过权限、结构、固定要求、目标方向和 `validate_and_solve()`。演示 `enforce` 与正式 `shadow` 都执行当前 `requirementPolicyVersion=1` 的硬边界。区分已证实无解与预算耗尽，两个分支都不得交付未经验证地图。候选可靠后冻结真实逐格 `executionBrief`，保留 `effect`、`anchors`、`focus`、`requiredTransitions`、`allowedOperators`、`preserve` 与 `playObjective`。视觉及游玩体验的结论各自说明验证范围。一条解法仅支持相应路线或指标，不能推出所有解法必经某序列。
5. 紫卡只对当前 Stage 的最新有效 `proposalOffer` 开放 `availableActions`，普通回复不使它过期。旧卡留作只读，后端拒绝过期 `sourceTurnId`，保留 `INVALID_CARD_SOURCE` 和 `PROPOSAL_STALE` 的各自适用条件。`execute_revision` 只重放原冻结差异并复验生成待审 proposal。采用时再确定性验证和求解，明确接受才创建新 Stage。拒绝、失效和失败均保留原图，旧冻结卡不得追加补偿修改。已可靠理解但有界搜索找不到候选时，可按原允许范围交付验证过的 Kimi 失败分析，保留原主题。理解、权限或上游异常各按原失败路径处理。

## 质疑、人工编辑与分歧

- 只用具体地图、求解、试玩或明确目标证据陈述风险。`WARNING` 是有证据的条件结果，意见不同、用户拒绝 AI、搜索失败或使用编辑器本身不构成警告。新的 `LET'S DISCUSS` 来自结构化分歧，历史卡片只走已有读取兼容。
- 标准 `REVISION` 卡按可用动作允许执行、质疑或替代。首次质疑只邀请说明理由，服务器保留两个暂定假设。清晰理由独立复核后生成一次 `ai_revision_challenge` 选择卡（`challengeCardSchemaVersion=2`），其余解释或含糊回复使用普通气泡。理由两次技术失败保留唯一用户回合和 `review_pending`，原键再试。明确替代理由使旧记录失效。挑战路由先于普通语义副作用。
- `choice_pending` 的“是”重验旧冻结差异并创建待审候选。“否”携带原申请及正式理由，在生成、修复、搜索中排除旧候选，生成仅允许 `execute_revision` 的新紫卡。按钮与明确文字触发同一状态转换。替代方向须与引用候选不同。保留现状 `retain_current` 结束分歧，不创建 Stage。
- 手工编辑通过保存校验即保留新 Stage。观察与基于已验证差异、求解/试玩、设计证据和有限 lineage 的比较共两条助手消息，成功时原子提交，评审失败可以恢复两条消息而不重复保存。观察无卡。比较仅在有具体冲突时增加一次入口 `LET'S DISCUSS`，不附带 `WARNING`，不自动撤回用户编辑。
- 后续人工编辑分歧使用普通气泡。`humanEditEngagement` 在入口判断 `engage / unchanged / unclear`。只有明确愿意讨论、解释、调整或重做且绑定最新原话和前置问题时，才记 `acknowledged`、解除提案阻塞。此状态只表明参与讨论。状态技术故障先局部修复。仍未核实则保留分歧和锁，交付可靠正文并按必要状态恢复处理。状态身份与 ID 由服务器生成。

## DesignContext、意图与问题进度

- `level_versions.design_context_json` 由服务端维护。子 Stage 克隆父 Stage 的快照后记录当前证据或决定，历史快照不吸收后代回答、忽略/恢复状态或证据。`explicit` 是用户明确说出，`confirmed` 来自用户确认或正式动作，`inferred` 是可纠正的推测。推测不能覆盖明确记忆或写成执行硬约束。
- Chat、Revision 和人工编辑复核使用不同投影。Revision 只取得相关、有效的 explicit/confirmed 目标、约束、确认/拒绝决定、开放问题及执行 brief。已拒绝、待定和推测倾向不得变成执行约束。用户自报告的 `designer_intentions` 独立于这套记忆。
- 可选 `designContextPatch` 验证来源，非法 patch 单独省略。明确记忆由用户语言建立，模型解释降为推测。普通非方案轮由主模型给 `intentDecision`，独立 `intent_candidate_review` 检查误报、漏报、原话和语义冲突。同时复核已提供的有限开放问题，模型只返回允许的 ID。已验证语义、问题结果和表达各自锁定。未展示候选可审计，不形成隐藏倾向。旧关键词结果标为 `legacy_unverified`，仅凭助手正文不得补出用户意图。模糊视觉反馈须保留对外观或玩法的语义不确定。
- 橙色 `TENTATIVE INTENT` 只在普通轮中可选显示，内容应有依据且便于修正。专用反馈接口才确认、修订或拒绝。拒绝无需模型。已有倾向时的确认及所有修订使用 `intent_feedback_review`。无法核实的结果维持原 ID 和待处理反馈，只有核实的同对象同属性反向 claims 可进入确定性新旧选择，其他冲突由语义复核。
- 当前进度分为 `Unresolved questions` 和确认或修订的 `Design inclinations`，记录来源 Stage，证据轨迹最多 12 条，限用户明确方向、正式决定及经验证的手工编辑证据。问题来自最终可见的非橙卡助手内容，已回答或忽略进入 `Processed`。忽略与恢复为确定性接口，不写额外聊天，也不调用模型。忽略期间从模型上下文排除，只能通过用户的 Restore 重新打开。Stage 开场不推进问题或已确认决定。

## 局部修复与必要状态恢复

- 技术失败先在原任务纠正机会内保留有效组件，锁定来源、目标、字段和类型，只修可定位项。不可解析回复用原有完整重试，不把空候选送给复核。有效语义拒绝保持拒绝。正式字段用证据绑定补丁，普通表达修复只交 `bodyParagraphs` 或 `cardText`。复核确认的正文缺陷使用原下一机会重验改变后的正文与锁定语义，不重做已核实的意图、卡片和问题。
- 上游理解、要求、合同或操作变化后，按依赖重新生成或校验候选、权限、快照、求解和冻结差异。快照可以补确定的来源格 `from`，不得猜造目标格、坐标、数量、用户约束或权限。提供者请求 Schema、解析器和局部修复指令必须一致，安全错误详情保留原阶段、失败原因和字段路径。
- 翻译按原 Turn 逐条保存成功项，失败保留源语言且仅重试未完成项。提示不接收快照内部字段，返回正文和路线文字仍按原 Turn 快照重验。原方案翻译独立复核使用既有第二次机会的 `accepted:boolean` 结构，拒绝或机会耗尽时保留原文。A/B 以完整题组回退。
- 人工编辑讨论的必要状态技术故障仍有可靠正文时，正文与只绑定该互动的恢复任务写在同一事务。任务保存在 `audit_events`，使用原用户/助手 Turn、原键、Stage、稳定分歧身份、状态和证据/地图签名。旧身份只从可唯一定位的入口事件读取，无法定位停止。当前界面在当前 Stage 可见且无写操作时可触发 `component-recoveries/{id}/retry`，总预算 10 秒、模型最多 8 秒、浏览器 12 秒，两次终身尝试，短事务领取租约 15 秒。原主请求预算不重置。
- 恢复只复核捕获原话、绑定问题及同 Stage 完整后续窗口（至多 24 条 Turn），保留撤回和替代证据。提交以 CAS 比对会话期限、最新用户顺序、状态、地图和 HTTP 守卫。较新消息已收到但尚未写 Turn 时也要等待或废弃旧结果。技术耗尽保留阻断，语义模糊作为 `needs_input`，无变化为 `completed_no_change`。成功只影响当前讨论阻塞，无新增卡片、地图、Stage 或历史改写。读取 `interactionState` 获取当前权威状态，GET 不触发模型。

## 审计和离线验证

- `requirements_verified` 只缓存完整验证结果。`reply_delivery_outcome`、`message_generation_failed`/`reply_generation_failed`、`reply_pipeline_diagnostic` 和 `component_recovery` 保留各自的任务、尝试、可恢复性和提交状态。诊断按请求、键、Stage 和允许的绑定定位原因，保留结构化错误和子诊断。首次失败是观察，补丁合并要与修后复验分开。诊断不记录正文、提示、原始输出、地图或凭据。前端在当前标签页保留有限的无正文诊断，服务端提交不证明用户收到或看到。
- `reliability_report.py` 以只读 SQLite 归并会话、任务、消息键，质疑理由并入相应消息，开场单列。正文交付、完整组件、方案验证、状态恢复和开场兜底分别统计。缺失项是未知，`rate` 以 `observed` 为分母。报告使用匿名引用和观测时间，错误码用于分类症状。多条记录不等于模型尝试次数或准确 HTTP 重试数。浏览器交付、审计前失败、人工语义质量及实际费用不由此表推定。

```powershell
python CoCreationPrototype/Backend/reliability_report.py path/to/local/cocreation.sqlite3 --since 2026-01-01T00:00:00Z --format text
```

- 普通回归使用本地 [验证命令](../README.md#本地验证)。接口测试用模型替身、临时存储及故障注入，协议测试通过真实请求构造后替换传输。覆盖语义局部修复、A/B 动作与旧收据、当前权限、冻结/采用、旧卡与原键重试、可选组件故障、迟到提交、人工保存/复核、翻译和诊断。相关入口为 [方案协议测试](Backend/tests/test_wire_contracts.py)、[A/B 回归](Backend/tests/test_binary_discovery.py)、[会话回归](Backend/tests/test_sessions.py)和[状态恢复测试](Backend/tests/test_component_recovery.py)。
- 独立语义评测按[评测说明](Backend/evaluations/README.md)执行。真实模型采样须有当前明确授权，隔离本地数据和 API 成本，不自动重放正式会话。离线固定输出验证程序路径，不作为真实模型准确率、线上可靠性或体验改善的证据。

## 8010 部署与回滚

此节适用于已经按 [AGENTS.md](../AGENTS.md#authorization-and-data-protection) 获得本轮明确授权的发布。

1. 对照已批准范围、版本和生产基线。通过 SQLite 在线 backup API 取得一致数据库备份，备份将替换的文件并保存 SHA-256 清单。WAL 模式下不要仅复制使用中的数据库主文件。生产配置备份按授权范围处理并保护凭据。
2. 8010-only 发布仅传送发生变化的 `CoCreationPrototype` 文件及新增模块。服务代码变更仅重启 `sokoban-cocreation`。独立诊断工具、文档和静态资源更新本身不要求 Python 服务重启。保留 8000、WebGL 及其他生产设置，不使用整仓部署脚本。
3. 核验源站及公网 health/ready、受影响的静态资源和预期未授权响应，按权限只读检查现存历史会话。线上无会话的共创入口会创建 Demo 并删除旧 Demo，验证时使用不写入研究数据的入口。
4. 如需代码回滚，恢复文件并按同一服务范围检查。保留发布期间新增数据，数据库备份只用于单独获准的数据恢复。

经授权的 WebGL 更新核对本地兼容构建、模板/资源缓存版本、公开入口与 loader、data、framework、wasm 响应。8000 服务代码的已授权发布只影响对应服务。环境状态和本地运维命令见 Git 忽略的 `SERVER.md`。
